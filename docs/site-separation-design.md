# แยกข้อมูลรายยาร์ด — 1 ยาร์ด = 1 ระเบียนต่อคัน (เอกสารออกแบบ ร่าง 1 · 6 ต.ค. 2569)

สถานะ: **รอตัดสินใจ** — ยังไม่มีการเปลี่ยนโค้ดหรือฐานข้อมูลตามเอกสารนี้

## 1. เป้าหมาย

- รถ 1 คัน ที่ผ่านหลายยาร์ด = หลายระเบียน ยาร์ดละระเบียน (เช่น NYB → 3D LCB = 2 ระเบียน)
- ระเบียนของยาร์ดเดิมหลัง Gate-out เป็น **ประวัติ** ไม่มีกระบวนการใดเขียนทับอีก
- Gate-in ที่ยาร์ดใหม่ = เริ่มกระบวนการใหม่ทั้งหมด (สถานะ ตำแหน่ง ประวัติ คิวงาน)
- ใช้ร่วมกันข้ามยาร์ด **เฉพาะ**: Defect (รายการตำหนิ+รูป) และผลตรวจ PDI / PM / FINAL CHECK
- Location / ตำแหน่งจอด / ผัง **ไม่**ใช้ร่วมกัน

## 2. โครงปัจจุบัน (สรุปจากโค้ด)

| ตาราง | กุญแจ | แยกยาร์ดด้วย | ปัญหา |
|---|---|---|---|
| `tracking_rows` | `vin` | คอลัมน์ `site` + ก้อน `__trips` (รอบที่ปิดแล้ว) ในแถวเดียวกัน | รถ 1 คันมีได้ยาร์ดเดียว การย้ายยาร์ด = เขียนทับแถวเดิม ต้องมีกลไกปิดรอบ/ก๊อปช่อง/กรองประวัติด้วยเวลา |
| `units` | `vin` | `site_id` | ย้ายยาร์ด = เปลี่ยนป้าย + ล้างช่อง สำเนาค้างบนเครื่องอื่นเขียนทับได้ |
| `damages` | `id` (+`vin`) | ไม่แยก (ถูกต้อง) | — |
| `visits` | `vin#round` | `site_id` | สร้างจาก `__trips` ตอนปิดรอบ ซ้ำซ้อนกับแนวใหม่ |
| `ops_queues` | `id` | `site_id` | items อ้าง `vin` อย่างเดียว |
| IndexedDB | `tracking`/`units` keyPath `vin` | — | ต้องเปลี่ยน |

## 3. โครงใหม่

### 3.1 `yard_cars` (แทน `tracking_rows`) — แถวชีตต่อยาร์ด

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `site_id` | text | **PK ส่วนที่ 1** |
| `vin` | text | **PK ส่วนที่ 2** |
| `cells` | jsonb | ช่องชีตของรอบนี้ (ไม่มี `__trips` อีก) |
| `history` | jsonb | ประวัติแก้ไขของรอบนี้เท่านั้น |
| `car_status` | text | สำเนาจาก cells เพื่อทำ index (`Pre Gate-in` / `In Yard` / `Gate-out` …) |
| `arrived_at` / `departed_at` | timestamptz | เวลาเข้า/ออกยาร์ดนี้ (null = ยังอยู่) |
| `updated_at`, `deleted_at` | timestamptz | เหมือนเดิม |

กฎที่ฐานข้อมูล:
- `unique (vin) where departed_at is null` — **VIN ละ 1 ระเบียนที่ยังเปิดอยู่ทั้งระบบ** (กันรถอยู่ 2 ยาร์ดพร้อมกัน) — ใช้ partial unique index
- index `(site_id, updated_at)` สำหรับดึงเฉพาะยาร์ด + sync ส่วนต่าง

### 3.2 `yard_units` (แทน `units`) — ตัวรถบนผังต่อยาร์ด

PK = `(site_id, vin)` คอลัมน์ที่เหลือเหมือน `units` เดิม (model/color/status/block/row/slot/gate_in_*/parked_at/…) ตัด `trip_count`, `last_pos` (เป็นของรอบ) ออก

- ระเบียนของยาร์ดเดิมหลัง Gate-out: `status = DEPARTED`, ช่องว่าง, ไม่ถูกเขียนอีก
- ระเบียนของยาร์ดใหม่: สร้างตอน Gate-in / Pre Gate-in / นำเข้าไฟล์ของยาร์ดนั้น

### 3.3 `damages` — ไม่เปลี่ยน (ใช้ร่วมกันตาม VIN)

เพิ่มคอลัมน์ `site_id` **เพื่อบันทึกว่าตำหนิถูกพบที่ยาร์ดไหน** (ไม่ใช้แยก แค่แสดง/รายงาน)

### 3.4 `station_checks` (ใหม่) — ช่องร่วมต่อคัน: PDI / PM / FINAL CHECK / ค่าวัด (ใช้ร่วมกันตาม VIN)

**แบบที่ทำจริงในขั้นที่ 1 (PR แรก):** เก็บ "ต่อช่อง" ไม่ใช่ต่อสถานี — 1 แถวต่อ (vin, key) โดย key คือชื่อช่องชีตเดิม
ทำให้ (ก) เขียนสองทางได้ที่จุดเดียว (`pushRows`) (ข) backfill เป็น SQL ตรง ๆ จาก `cells` (ค) ประวัติ RE-PDI/PM1–15
ยังเป็นบันไดคีย์เหมือนเดิม ไม่ต้องแปลงโครง และรองรับการตัดสินใจข้อ 6.2 ได้ทั้งสองทางในขั้นถัดไป

| คอลัมน์ | หมายเหตุ |
|---|---|
| `vin`, `key` | PK = `(vin, key)` · key = ชื่อช่องชีตเดิม (`PDI`, `RE PDI  Date #1`, `PM3`, `Final check date`, `% SOC`, …) |
| `value` | ค่าล่าสุด ('' = ถูกล้าง) |
| `at`, `by`, `src` | เวลา/ผู้บันทึก/ที่มา (`scan` สถานี · `admin` · `import` · `backfill`) จาก history ของแถว |
| `site_id` | ยาร์ดที่บันทึก (แสดง/รายงาน ไม่ใช้แยกข้อมูล) |

ช่องที่นับเป็น "ช่องร่วม" (`SHARED_VIN_KEYS` ใน `src/lib/stationChecks.ts`): `ROUND_COPIED_KEYS` ทั้งชุด
(Status, Vin Of Status, Final Status, Final check date, OK date, PIC (PDI), % SOC, Tire Pressure, Aging PM, PDI_KEYS, PM_KEYS)
+ ค่าวัดของสถานี (Tire Pressure FL/FR/RL/RR, Mileage, Voltage of 12V)

ขั้นที่ 1 ส่งขึ้น: SQL `supabase-station-checks.sql` (ตาราง + backfill ไม่ทับค่าที่แอปเขียนแล้ว) · แอปเขียนสองทางที่
`pushRows` (เทียบกับค่าที่เครื่องรู้ครั้งก่อน ส่งเฉพาะที่เปลี่ยน ส่งไม่สำเร็จ `syncCloud` ส่งซ้ำ) · เครื่องมือตรวจใน
Settings (อ่านอย่างเดียว) — **การอ่านยังมาจากชีต** จนกว่าเครื่องมือตรวจจะยืนยันว่าตรงกันทั้งยาร์ด แล้วจึงสลับ (ขั้น 1b)

**ต้องตัดสินใจ (ข้อ 6.2):** "ใช้ร่วมกัน" หมายถึงตรวจครั้งเดียวทั้งชีวิตรถ หรือแค่ "เห็นผลเก่าได้ แต่ยาร์ดใหม่ต้องตรวจใหม่" —
กำหนดว่าคิวงานของยาร์ดใหม่ถือว่าผ่านแล้วหรือไม่ (โครงตารางรองรับทั้งสองทาง)

### 3.5 `visits` — เลิกใช้ (ระเบียน `yard_cars` ที่ `departed_at` ไม่ว่างคือ visit ในตัว)

### 3.6 `ops_queues` — เหมือนเดิม (แยกยาร์ดอยู่แล้ว) items อ้าง `vin` ภายในยาร์ดของคิว

## 4. กติกาการทำงาน

| เหตุการณ์ | ของใหม่ |
|---|---|
| Pre Gate-in (ไฟล์/Shuttle/แอดมิน) ที่ยาร์ด B | สร้าง `yard_cars(B, vin)` สถานะ Pre Gate-in — **ไม่แตะ** ระเบียนของยาร์ด A |
| Gate-in ที่ B | ถ้ามีระเบียนเปิดอยู่ที่ A (`departed_at null`) → **ปฏิเสธ** บอกว่ายังไม่ Gate-out จาก A (การ์ดเดิม ย้ายมาถามคลาวด์ข้ามยาร์ด) · ผ่าน → สร้าง/อัปเดต `yard_units(B, vin)` |
| Gate-out ที่ A | `yard_cars(A)` ตั้ง `departed_at` + Car Status Gate-out, `yard_units(A)` DEPARTED ล้างช่อง, เขียน Last Yard Location ครั้งเดียว — จบ ไม่มีการ "เปิดรอบใหม่" ที่ปลายทางอัตโนมัติ (ปลายทางสร้างเองตอน Pre Gate-in/Gate-in) |
| Relocation ที่ B | เขียน `yard_units(B, vin)` เท่านั้น ไม่มีป้ายยาร์ดให้เทียบ ไม่มีตัวกวาดข้ามยาร์ด |
| Defect | เขียน `damages(vin)` + `site_id` ยาร์ดที่พบ · หน้า Damages ของ B = damages ของ VIN ที่มี `yard_cars(B)` เปิดอยู่ |
| PDI/PM/FINAL | เขียน `station_checks(vin, station)` · คิวงานของ B อ่านตารางนี้ |
| ไฟล์ Tracking / Vin List (ทั้งบริษัท ไม่ระบุยาร์ด) | **ต้องตัดสินใจ (ข้อ 6.1)** — ค่าเริ่มต้นที่เสนอ: อัปเดต "ระเบียนที่ยังเปิดอยู่ของ VIN นั้น" ยาร์ดไหนก็ได้; VIN ที่ไม่มีระเบียนเปิด → สร้างที่ยาร์ดที่เลือกอยู่ (Pre Gate-in) |
| ไฟล์ Co-Inspection / Lane / Grouping / PM queue / Accessory | ผูกกับยาร์ดที่เลือกอยู่เท่านั้น (เหมือนที่การ์ดครึ่งหนึ่งทำอยู่) |
| ค้นหา VIN (Unit List, ท้าย 5 ตัว, ใบหารถ, Report 2PS) | ค้นทุกยาร์ด → แสดง "ระเบียนที่เปิดอยู่" เป็นหลัก + ประวัติยาร์ดอื่นเรียงตามเวลา |
| Dashboard / Yard plan / สถานี ops | อ่านเฉพาะ `site_id = ยาร์ดที่เลือก` — เร็วขึ้น ไม่ดึงยาร์ดอื่น |

## 5. แผนทำเป็นขั้น (deploy แยก ย้อนได้ทีละขั้น)

| ขั้น | งาน | ประมาณ | ย้อนกลับ |
|---|---|---|---|
| 0 | เอกสารนี้ + ตัดสินใจข้อ 6 · สำรองฐานข้อมูลเต็ม (Supabase backup + export CSV 10 ตาราง) | 0.5 วัน | — |
| 1 | `station_checks`: สร้างตาราง + backfill จากช่องชีต · แอปเขียนสองทาง (ชีต+ตาราง) · เครื่องมือตรวจความตรงกัน — **ยังอ่านจากชีต** | 1 วัน (ทำแล้ว) | ไม่ต้องทำอะไร (แอปรุ่นก่อนไม่รู้จักตาราง) |
| 1b | สลับการอ่าน Unit List/สถานี/รายงาน ไปใช้ตาราง หลังเครื่องมือตรวจยืนยันตรงกัน | 1–2 วัน | ปิดการอ่านจากตาราง กลับไปอ่านชีต |
| 2 | `yard_units`: สร้างตาราง · migrate จาก `units` (1 แถว → 1 แถวที่ `site_id` เดิม; DEPARTED ที่ไม่มี site → ข้าม) · IDB bump · realtime/sync bus ส่ง site · ผัง/Relocation/Gate-in/Gate-out/Driver/ใบหารถ/Grouping | 3–4 วัน | ตารางเก่าไม่ถูกแตะ — deploy build เก่า |
| 3 | `yard_cars`: สร้างตาราง · migrate 54k แถว: แถวปัจจุบัน → `(site, vin)` เปิดอยู่; แต่ละก้อนใน `__trips` และแถว `visits` → ระเบียนปิดแล้วของยาร์ดนั้น · partial unique · 8 โมดูลไฟล์ · Units/ค้นหา/Report/Event · เลิกใช้ `visits`/`__trips`/`roundHistory`/`closeRoundRow`/`TRIP_SCOPED_KEYS` | 5–7 วัน + ซ้อม migrate บนสำเนา 1 รอบ | ยากขึ้น: ข้อมูลที่เขียนลงตารางใหม่ระหว่างย้อนจะหาย |
| 4 | ถอดโค้ดเก่า (ตาราง/กลไกรอบ) หลังใช้งานจริง 2 สัปดาห์ | 1 วัน | — |

Cutover ของขั้น 2 และ 3 (ครั้งละ ~30–60 นาที นอกเวลางาน):
1. ประกาศหยุดนำเข้าไฟล์/สแกน
2. รัน migrate SQL (idempotent — รันซ้ำได้)
3. deploy build ใหม่ · build ใหม่มี **เวอร์ชันข้อมูลขั้นต่ำ** — เครื่องที่ยังเป็น build เก่าจะถูกบังคับรีเฟรชผ่านกลไกอัปเดต PWA และ `app_config` (ปฏิเสธเขียนถ้าเวอร์ชันต่ำกว่า)
4. ทุกเครื่องเปิดครั้งแรก: ล้าง IndexedDB แล้วโหลดเฉพาะยาร์ดที่เลือก (หน้า Loading NN% ที่มีอยู่)
5. ตรวจยอด: In Yard / ผัง / คิวงาน ต่อยาร์ด ต้องเท่ากับก่อน cutover (เตรียม SQL เทียบยอดไว้ล่วงหน้า)

## 6. ต้องตัดสินใจก่อนเริ่มขั้น 1

1. **ไฟล์ master ที่ไม่ระบุยาร์ด** (Tracking / Vin List / Dealer): อัปเดตระเบียนที่เปิดอยู่ของ VIN นั้นไม่ว่ายาร์ดไหน (เสนอ) หรือเฉพาะยาร์ดที่เลือกอยู่
2. **PDI / PM / FINAL ข้ามยาร์ด**: (ก) ตรวจครั้งเดียว ยาร์ดใหม่ถือว่าผ่าน — คิวงานข้ามให้ · (ข) เห็นผลเก่าได้ แต่ยาร์ดใหม่ต้องตรวจใหม่ (ตารางเก็บผลล่าสุด + ประวัติ)
3. **Defect จากยาร์ดอื่น**: ช่างที่ยาร์ดใหม่เห็นและซ่อมต่อได้เลย (เสนอ) หรือเห็นอย่างเดียว
4. **Gate-in ที่ปลายทางก่อนต้นทาง Gate-out** (ไฟล์มาช้า): ปฏิเสธเสมอ (เสนอ — ให้ต้นทางยิงออกก่อน) หรือยอมให้แอดมินบังคับ
5. **ช่วงเวลา cutover** ของขั้น 2 และ 3 (นอกเวลางานวันไหน)
6. ย้ายข้อมูลประวัติเก่าที่ไม่มี `__trips` (รอบก่อน 19 ก.ย.): สร้างระเบียนปิดแล้วแบบ "มีแค่วันที่เข้า/ออก" หรือไม่สร้าง

## 7. ที่ไม่เปลี่ยน / ต้องทำแยก

- RLS ยัง allow-all (ความปลอดภัยเท่าเดิม) — ถ้าต้องการกั้นที่ฐานข้อมูลเป็นงานอีกชุด
- ช่องโหว่ข้อ ค (เครื่องค้างเขียนทับทั้งแถว) — แก้ระหว่างขั้น 2 ได้พร้อมกัน (การเขียนตำแหน่งส่งเฉพาะคอลัมน์ตำแหน่ง)
- ปัญหา Relocation โหมดแถว 4 ข้อที่รีวิวไว้ — แก้ได้ก่อนหรือหลัง ไม่ขึ้นกับโครง
- กล้อง / ความเร็วโหลด — ไม่เกี่ยว
