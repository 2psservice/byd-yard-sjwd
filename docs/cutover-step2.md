# Cutover ขั้น 2 — สลับแอปไปใช้ตารางรถรายยาร์ด (`yard_units`)

ผู้ดำเนินการ: แอดมินที่มีสิทธิ์ Supabase (เข้า SQL Editor ได้) · เวลา: **14 ต.ค. 2569 เริ่ม 23:00** · ใช้เวลาจริงราว 30–45 นาที
ออกแบบ: `docs/site-separation-design.md` §5.1 · ไฟล์ SQL ทั้งหมดอยู่ที่รากโปรเจกต์ (เปิดเป็นข้อความ คัดลอกไปวางใน Supabase → SQL Editor → Run)

## ภาพรวม — ทำไมปลอดภัย

- แอปเวอร์ชันใหม่ **ขึ้นไปก่อนแล้วแบบปิดสวิตช์** — จนกว่าจะรันไฟล์ `flip` แอปทุกเครื่องทำงานเหมือนเดิมทุกอย่าง (ใช้ตาราง `units`)
- ตาราง `units` เดิม **ไม่ถูกลบ/ไม่ถูกแก้ตัวข้อมูล** — ย้อนกลับได้ด้วยไฟล์ `rollback` (ข้อมูลที่เขียนลงตารางใหม่หลังสลับจะไม่ตามกลับไป)
- หลังสลับ ตาราง `units` ถูกปิดการ "แก้" เครื่องที่ยังเป็นแอปรุ่นเก่าจะเห็นข้อความบันทึกไม่สำเร็จ (แทนที่จะยิงแล้วไม่ขึ้นเงียบ ๆ) แล้วอัปเดตเป็นรุ่นใหม่เอง
- เครื่องที่เปิดแอปอยู่ตอนสลับ จะเห็นป้ายเต็มจอ "ระบบปรับโครงสร้างข้อมูลรถแล้ว" ภายใน ~30 วินาที แล้วรีเฟรชเองใน 15 วินาที

## ลำดับเวลา

**ก่อน 22:30 (เตรียม)**

2. ถ่ายภาพ **Yard Plan ของทุกยาร์ด** (ตัวเลข In Yard · ในช่องจอด · ยังไม่มีตำแหน่ง) เก็บไว้เทียบหลังสลับ
3. แจ้งหน้างานว่า **23:00 หยุดสแกน/นำเข้าไฟล์ทุกอย่างจนกว่าจะแจ้งใหม่** (ใช้เวลาราว 30–45 นาที)

**22:30 — ขั้น 1 (ก่อนเวลาได้ ไม่กระทบหน้างาน)**
4. รัน `supabase-yard-units.sql` ทั้งไฟล์ แล้วดูตารางผลตรวจยอดตอนท้าย (แต่ละยาร์ด: `units` ต้องเท่ากับ `yard_units`)

**23:00 — หยุดสแกน**
5. ยืนยันกับหน้างานว่าหยุดแล้ว (ไม่มีใครยิง Relocation / Gate-in / Gate-out / นำเข้าไฟล์)

**23:05 — ขั้น 2 สำรองข้อมูล**


   (`--no-photos` ข้ามรูป defect เพราะการสลับครั้งนี้ไม่แตะตาราง `damages`) · ต้องจบด้วย "สำรองครบทุกตาราง" — ถ้าขึ้น "ไม่ครบ" **หยุด** ห้ามไปขั้นต่อไป

**23:20 — ขั้น 3 คัดลอกล่าสุด + ตรวจยอด**
7. รัน `supabase-yard-units-cutover.sql` ทั้งไฟล์ → ดูตารางผลตรวจยอดตอนท้าย **ทุกแถวต้องได้ `ok = true`**
   ถ้ามีแถว `false` **หยุด** แล้วส่งภาพผลมาให้ผม

**23:25 — ขั้น 4 สลับ**

**23:27 — ตรวจ**

10. เทียบ Yard Plan ทุกยาร์ดกับภาพที่ถ่ายไว้ — ตัวเลข In Yard / ในช่อง / ยังไม่มีตำแหน่ง **ต้องเท่าเดิม**
11. ทดสอบ 1 คัน: เปิดรถคันหนึ่ง ยิง Relocation ไปช่องว่าง ดูว่าขึ้นบนผังและเครื่องที่สองเห็นด้วย
12. ถ้าครบ → แจ้งหน้างานให้ **รีเฟรชแอปแล้วกลับมาสแกนได้** (เครื่องที่ค้างอยู่จะเห็นป้ายเอง)

## ถ้ามีปัญหา — ย้อนกลับ

รัน `supabase-yard-units-rollback.sql` แล้วให้ทุกเครื่องรีเฟรช (เครื่องที่เปิดอยู่เห็นป้ายเอง) แอปกลับไปใช้ `units` ตามสภาพ ณ ตอนสลับ
ข้อมูลที่เขียนลง `yard_units` หลังสลับ **ไม่ตามกลับไป** — ถ้าหน้างานสแกนไปแล้วช่วงหนึ่ง ต้องยิงใหม่เฉพาะคันนั้น

ควรย้อนกลับเมื่อ: ตัวเลขยอดไม่เท่าก่อนสลับ · ยิง Relocation แล้วไม่ขึ้น · ผังว่างทั้งที่ควรมีรถ · เครื่องส่วนใหญ่ขึ้นข้อความบันทึกไม่สำเร็จ

## ข้อควรรู้

- **รถที่ไม่มีป้ายยาร์ดในตาราง `units`** (รถเก่า) **ไม่ถูกย้าย** (ตัดสินใจแล้ว 14 ต.ค.: เป็นข้อมูลที่ไม่ได้ใช้ รถทุกคันมียาร์ดของตัวเอง) — ไม่ลบอะไรออกจาก `units` แค่ไม่คัดลอกไปตารางใหม่ · ตอนรันไฟล์ `supabase-yard-units.sql` / `cutover` มีตารางสรุปท้ายไฟล์บอกจำนวน (`untagged_total`) และที่ยังมีช่องจอดค้าง (`untagged_with_slot` — กลุ่มนี้จะไม่ขึ้นผังหลังสลับ) ถ้า `untagged_with_slot` ไม่ใช่ 0 ให้บอกผมก่อนสลับ
- **รถ 1 คันอยู่ได้หลายยาร์ด:** ยิง Gate-out ที่ยาร์ดต้นทาง = แถวต้นทางปิด (ประวัติ ไม่มีใครเขียนทับ) ปลายทางได้แถวใหม่ของตัวเอง
- การตรวจตำแหน่งที่หายแบบเดิม (ยกเลิก Gate-out แล้วคืนช่อง · งานคืนตำแหน่งครั้งเดียว) ทำงานต่อได้ในโหมดใหม่ — ทำเฉพาะยาร์ดที่เลือกอยู่
- ขั้น 3 (แยกแถวชีตต่อยาร์ด) **ยังไม่ทำ** — ทำทีหลังเมื่อขั้นนี้เสถียร
